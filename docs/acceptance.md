# Итоговая приемка LedgerCore

Фактическая дата выполнения и проверок: 29.10.2026, Europe/Moscow. Git использует заданные исторические метаданные 08.05–24.08.2025. Нет утверждений о коммерческой эксплуатации, внешних пользователях или реальных платежах.

## Реализация

Реализован сервис Go/net/http + PostgreSQL 17.9 + pgx/v5: клиентские RUB-кошельки с нулевым балансом, защищенный системный счет, сбалансированное административное финансирование, переводы, полная отмена, история и независимая сверка. Деньги — проверенный int64, HTTP-строки, SQL BIGINT; агрегаты сверки — NUMERIC.

Права прикладной роли не позволяют UPDATE/DELETE/TRUNCATE журнала. Отложенные триггеры проверяют не только проводки, но и заголовок без записей. Уникальность отмены и ключа идемпотентности обеспечена БД. Счета блокируются по UUID в одном порядке. Конечные бизнес-отказы сохраняются вместе с успехами; инфраструктурные ошибки откатываются. Есть deadline-aware retry всей транзакции, статическая bearer-аутентификация, лимиты, таймауты, отдельный listener метрик и bounded shutdown.

CLI включает `migrate`, `fixture --allow-test-funds`, `demo`, `reconcile`, `bench`, `explain`. Dockerfile многоэтапный и non-root; Compose хранит данные отдельно; CI содержит обязательные интеграционные проверки. README, OpenAPI, инварианты, архитектура и четыре ADR находятся в репозитории.

В интеграционных тестах проверены:

1. Конкурентные списания с одного источника не превышают средства и не дают отрицательного остатка.
2. Множество одинаковых ключей создает одну операцию; нормализованные запросы повторяются, измененные параметры конфликтуют.
3. Отброшенный результат после commit возвращается тем же ключом.
4. Окончательный отказ остается отказом после финансирования, в том числе при 32 одновременных запросах с одним ключом.
5. Встречные переводы и отмены сохраняют инварианты; одновременно из 32 отмен проходит одна.
6. Уже потраченные средства, повторная отмена, отмена финансирования и отмены корректно отклоняются.
7. Пустые, несбалансированные, неверно направленные и лишние проводки не проходят commit.
8. Прикладная роль не переписывает журнал, не создает системные счета и не финансирует кошельки. К старому заголовку нельзя дописать запись.
9. Проверены overflow, независимое обнаружение административной порчи проекции и восстановление только самим тестом.
10. Последовательная случайная модель с фиксированным seed сравнивает состояние БД после каждого шага; конкурентные проверки не требуют заранее известного порядка commit.
11. Snapshot-сверка под записью не выдает ложных расхождений; пагинация не повторяет записи исходного набора.
12. Убитый до commit процесс не оставляет ни части перевода, ни idempotency-результата. SQLSTATE40001 приводит к повтору; три неудачные попытки ограничены и не оставляют состояние; row-lock deadline учитывается.

Unit-тесты отдельно проверяют Money, max/min int64, нормализацию, включение метаданных в fingerprint, чистую модель 10000 переходов, cursor validation, HTTP bounds/auth/errors, bounded metric labels и закрытие заблокированного пула в пределах бюджета.

Аварийные триггеры находятся только в тестовом исходнике. Их выполнение требует отдельной БД с `test` в имени; реальные LOGIN-роли проверяются тестовым harness. Процесс останавливается после наблюдения advisory-lock barrier в `pg_locks`, без предположения о времени выполнения по sleep.

## NOT RUN и ограничения

- **NOT RUN: Docker build, чистый Compose startup и контейнерный SIGTERM.** Docker Desktop 4.41.2 падает при инициализации inference manager. Выполнены независимые native-проверки, синтаксис Compose и shell. Воспроизведение при работающем движке: `make up`, `make test-integration`, `make demo`, `docker compose stop -t12 api`, `make down`.
- **На момент исходной локальной приемки — NOT RUN: hosted GitHub Actions.** Репозиторий тогда еще не публиковался. Workflow готов; первоначальная приемка не заявляет результаты внешнего CI.
- **NOT RUN: реальный Linux SIGTERM-прогон.** В Windows выполнены unit-тесты общего бюджета завершения и аварийное убийство процесса до commit. Обработчик SIGTERM и drain реализованы; реальное контейнерное завершение требует доступного Docker.
- **NOT RUN: полный OpenAPI schema-validator.** Выполнен YAML-парсинг и проверка всех локальных ссылок. HTTP-контракт покрыт тестами обработчиков и реальной демонстрацией.

Идемпотентность общая для одного доверенного контура и хранится без TTL; размер БД растет. Аутентификация не заменяет учет пользователей и владельцев кошельков. Прикладная роль может изменять необходимые ей столбцы проекции: нарушение выявит сверка. Администратор БД не входит в модель защиты. Полное финансирование ограничено int64 системного остатка. Успешный перевод на реальной БД с суммой MaxInt64 отдельно не измерялся; максимальный парсинг/арифметика проверены unit-тестами, переполнение проекции — реальным интеграционным тестом.

Во время ревью исправлены реальные проблемы: benchmark принимал произвольный 4xx за бизнес-отказ; синхронный `pool.Close` мог превысить shutdown budget; окончания строк локального SQL отличались от чистого checkout и могли изменить checksum. Теперь классификация проверяет смысл ответа, закрытие пула имеет общий deadline, SQL использует LF и проверяется тестом. Для финальной приемки созданы новые пустые БД; сохраненные checksums старых экспериментальных БД не переписывались.

## Вопросы для собеседования

1. **Почему READ COMMITTED достаточно?** Каждая операция заранее знает два счета и блокирует обе строки по UUID. Проверка средств и изменение остатков происходят под этими блокировками в одной транзакции, поэтому параллельные списания сериализуются.
2. **Как обработан конкурентный Idempotency-Key?** INSERT под уникальным `(kind,key)` ждет первую транзакцию. Следующий SELECT видит ее окончательный результат; rollback удаляет reservation. Fingerprint отличает измененные параметры.
3. **Зачем сохранять insufficient_funds?** Иначе одинаковый запрос с тем же ключом мог бы стать новой успешной операцией после пополнения. Здесь повтор возвращает исходный отказ; новая попытка пользователя получает новый ключ.
4. **Что делать при разрыве соединения на commit?** Исход неизвестен. Повторить тот же ключ и параметры; нельзя считать перевод неуспешным и отправлять его с новым ключом.
5. **Почему не CHECK(sum(delta)=0)?** CHECK относится к одной строке. Deferred constraint triggers на заголовке и проводках проверяют состояние всей операции при commit, включая пустой заголовок и точное направление двух записей.
6. **Защищает ли неизменяемость от DBA?** Нет. Runtime-роль не имеет прав переписывания журнала; отдельные триггеры запрещают изменение и дописывание к старому заголовку. Владелец/суперпользователь может обойти ограничения.
7. **Почему нельзя отменять перевод UPDATE-ом?** Это удалило бы аудиторский след. Отмена — новая противоположная операция с unique-ссылкой на обычный перевод и проверкой доступных обратных средств.
8. **Почему сверка использует NUMERIC и snapshot?** Сумма многих int64-проводок может временно превысить int64; NUMERIC не переполняется. REPEATABLE READ READ ONLY исключает сравнение журнала и проекции из разных моментов.
9. **Почему cursor не основан на времени?** Время/общая последовательность могут выделяться до commit. Локальная последовательность счета назначается под той же блокировкой; верхняя граница первой страницы исключает поздние записи из исходного набора.
10. **Что показала нагрузка и что оптимизировано?** При 32 клиентах независимые пары значительно быстрее общей пары в данном прогоне. EXPLAIN выявил устаревшую статистику; после ANALYZE уже существующий индекс дал обратное сканирование. Новые индексы и смена изоляции без достаточных измерений не добавлялись.
