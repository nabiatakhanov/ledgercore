# LedgerCore invariants (design contract, written before implementation)

This is an educational internal ledger with test funds, one currency (RUB), no bank connection.

1. An operation amount is a strictly positive integer number of kopecks, at most 9223372036854775807. HTTP represents money as decimal strings. Go uses checked int64 arithmetic, PostgreSQL uses BIGINT. No floating point money.
2. A signed posting delta increases (+) or decreases (-) an internal balance. Each transaction has exactly two postings on different accounts, -amount on the source and +amount on the destination, total zero. This is a normalized double entry model: wallet liabilities grow on credit and shrink on debit; debit is not universally a decrease for all accounting account types.
3. Client accounts start at zero and remain nonnegative. Only a protected balancing system account may be negative. Public requests cannot debit or credit system accounts. Administrative fixtures fund clients through the same balanced transaction writer, using a distinct DB role and stable idempotency keys.
4. Committed journal transactions and postings are append only. Reversal appends a full opposite transaction linked to an ordinary transfer. A transfer has at most one reversal. Funding and reversals cannot be reversed. Insufficient reverse funds leave no partial change.
5. The journal is authoritative; accounts.balance_minor is a synchronous projection updated in the same transaction. Each individual new balance is checked for int64 overflow. Reconciliation sums with PostgreSQL NUMERIC, not BIGINT.
6. A deferred constraint trigger checks both headers and postings at commit: exactly two, sum zero, exact accounts, exact amount and signs, valid operation/account types and reversal relationship. Empty headers cannot commit. FK, CHECK and UNIQUE constraints enforce local invariants. Runtime roles cannot UPDATE/DELETE/TRUNCATE journal rows or append postings to previously committed headers.
7. The writer uses READ COMMITTED and locks both account rows in ascending UUID order for all operation types. Idempotency reservation precedes account locks. Reversal races resolve under the same account locks plus a unique original-transaction reference. No external calls under locks.
8. Operation kind + key is unique. Canonical IDs, amount, currency and all metadata contribute to the fingerprint. Identical requests replay the stored status/body, including terminal business failures. Parse and infrastructure failures are not persisted. Concurrent keys wait for commit within deadlines. Only SQLSTATE 40001/40P01 retry the whole transaction, bounded and context aware.
9. Success is returned only after commit. Commit connection loss is an unknown outcome; retry with the same key and parameters. A rollback or process death before commit leaves neither half-transfer nor cached success.
10. Account reads are single-statement committed snapshots. History uses descending account-local sequence numbers assigned under the account lock; its first page fixes an upper bound, so later commits cannot introduce entries behind the cursor. Reconciliation uses one REPEATABLE READ READ ONLY snapshot for all checks.
11. Reconciliation independently checks projection equality, negative clients, malformed/empty/unbalanced transactions and reversal eligibility/uniqueness; it never repairs. A privileged administrator can bypass protections: the system does not claim protection against DB owners. Projection changes outside the writer are detected by reconciliation.
12. API bearer authentication defines one trusted internal scope, not per-user authorization. Bodies, metadata, pages, timeouts and pool sizes are bounded. Logs and metric labels contain no credentials, idempotency keys or sensitive metadata. Fault injection is compiled only into tests and crash experiments use a separate database.
