# Промпт: расширить LedgerCore — Kafka, gRPC и Redis в одном проекте

Ты — самостоятельный Go backend-разработчик уровня middle. Расширь существующий LedgerCore до сервиса переводов с событийной историей операций. Цель — законченная проверяемая реализация Kafka, gRPC и Redis, которую можно описать одним проектом в резюме.

Исходный репозиторий: https://github.com/nabiatakhanov/ledgercore . Если локальная копия уже предоставлена, работай с ней. Это развитие одного проекта, а не создание еще одного независимого пункта портфолио.

Работай непосредственно с файлами, терминалом и Git. Нужны рабочая интеграция, тесты с настоящей инфраструктурой, документация, воспроизводимые эксперименты и последовательные содержательные коммиты.

## 1. Сначала изучи существующую реализацию

Прочитай AGENTS.md и аналогичные инструкции, README, схему БД, бизнес-логику, идемпотентность, тесты, CI и отчеты. Зафиксируй текущую ветку, git status и базовый commit SHA. Сохрани чужие изменения и создай отдельную рабочую ветку.

Запусти доступные исходные проверки и обозначь результат. Если доступа к исходникам нет, сообщи об этом и запроси репозиторий или архив; не выдавай новую несвязанную реализацию за интеграцию с LedgerCore.

Не останавливайся после плана. Реализуй расширение последовательно и доведи до критериев приемки. Выбирай поддерживаемые стабильные версии по официальной документации, фиксируй версии Go, Protobuf-инструментов, клиентов и Docker-образов. Не используй latest.

Если часть проверки невозможно выполнить, обозначь NOT RUN, причину и команду воспроизведения. Не выдумывай результаты тестов или бенчмарков.

## 2. Архитектура и назначение технологий

Реализуй три небольших сервиса:
1. Gateway — HTTP API для клиента. Обращается к LedgerCore и Activity по gRPC; использует Redis для общего rate limiter.
2. LedgerCore — существующая бизнес-логика, исходный PostgreSQL и новый gRPC-адаптер. Сохраняет перевод и событие outbox в одной транзакции. Publisher доставляет события в Kafka.
3. Activity — Kafka consumer, собственная PostgreSQL-проекция активности и gRPC API чтения истории/сводки.

Publisher может быть отдельным исполняемым процессом того же компонента LedgerCore. Gateway запускается минимум в двух экземплярах для проверки общего Redis-лимита. Activity допускает несколько экземпляров в одной consumer group.

Роли:
- PostgreSQL LedgerCore — источник истины о средствах, журнале и идемпотентности.
- Kafka — асинхронная доставка событий уже совершенных операций.
- PostgreSQL Activity — восстанавливаемая модель чтения активности.
- gRPC — реальные межпроцессные вызовы Gateway → LedgerCore и Gateway → Activity.
- Redis — общий rate limiter нескольких Gateway, не источник истины о деньгах.

В Compose допустим один PostgreSQL-сервер с отдельными БД и ролями сервисов. Не читай таблицы другого сервиса напрямую и не делай общую транзакцию между этими БД.

Ограничь масштаб: без Kubernetes, service mesh, Schema Registry, реальных банков, фронтенда, платежных шлюзов и собственной реализации брокера. Redis-кеш денежных остатков в эту версию не входит.

## 3. Сохрани финансовые инварианты

Не переписывай работающую бизнес-логику ради транспорта. gRPC и существующий HTTP должны использовать одинаковые application-сценарии.

Сохрани:
- Двойную запись, неизменяемый журнал и целочисленные денежные значения.
- Проверку остатка и упорядоченные блокировки счетов.
- Идемпотентность операций и правила полной отмены.
- Независимую сверку в согласованном snapshot.
- Отсутствие частично зафиксированного перевода.

Существующие API-контракты и тесты не должны незаметно ломаться. Старый HTTP-адаптер можно сохранить как внутренний/совместимый интерфейс; документируй рекомендуемую точку входа Gateway и порты. Не дублируй финансовый алгоритм в Gateway или Activity.

Kafka и Redis не должны участвовать в SQL-транзакции списания. Не выполняй сетевую публикацию в Kafka под блокировками счетов. Чтение Activity явно eventually consistent; оно не применяется для проверки доступных средств.

## 4. gRPC и Protobuf

Определи минимум два контракта:
- LedgerService: CreateTransfer, GetTransfer, ReverseTransfer.
- ActivityService: GetAccountActivity с ограниченным размером страницы и стабильным cursor.

Сверь набор полей с реальным API LedgerCore. Передавай постоянный ключ идемпотентности для команд. В Protobuf денежные значения имеют явно заданную целочисленную семантику; внешний HTTP сохраняет согласованный формат amount_minor. Не используй float для денег.

Требования:
- Версионированные proto packages, фиксированные версии генераторов и воспроизводимая make generate.
- Не переиспользуй номера удаленных полей; additive-изменения не должны ломать существующих клиентов.
- Context, явные deadlines, отмена и ограниченные размеры сообщений.
- Interceptors для request_id, безопасных логов и метрик.
- Документированное сопоставление бизнес-ошибок с gRPC status и HTTP-кодами; внутренние SQL-ошибки наружу не выдаются.
- Ограниченные повторы только применимых transient-ошибок. Команда повторяется с тем же ключом; новый ключ на каждом retry запрещен.
- DEADLINE_EXCEEDED или разрыв ответа не означают, что транзакция точно не зафиксировалась. Продемонстрируй выяснение исхода через тот же ключ или ID операции.
- Health checks и bounded graceful shutdown.

Для локального приватного Docker-сегмента допустим plaintext gRPC с явной документацией ограничения. Внутренние write-порты не публикуй как незащищенную внешнюю точку обхода Gateway. Не называй демонстрационный контур банковской production-инфраструктурой.

## 5. Transactional Outbox и Kafka producer

Добавь outbox в БД LedgerCore. Успешный перевод или отмена и соответствующее событие записываются одной SQL-транзакцией. Отказ и rollback не создают событие. Повтор идемпотентного запроса не создает новую бизнес-операцию или новое логическое событие.

Событие имеет стабильные event_id, schema_version, type, journal_transaction_id, occurred_at, from/to account IDs, сумму, валюту и при необходимости ссылку на исходную отменяемую операцию. Не включай секреты и токены. Для Kafka достаточно документированного JSON-контракта; денежные значения кодируются без потери точности.

Выбери topic и key. Для первой версии подходит key по journal_transaction_id. Гарантируется порядок только внутри partition, не глобальный порядок всех счетов. Проекция должна быть корректна при перестановке независимых событий и позднем поступлении отмены.

Publisher:
- Захватывает ограниченную пачку outbox с короткой SQL-транзакцией и безопасным протоколом владения/аренды.
- Публикует после завершения транзакции захвата, не удерживая соединение и блокировки во время сетевого ожидания.
- Использует acks=all, идемпотентный producer при поддержке выбранного клиента, разумные таймауты и ограниченный backoff. Зафиксируй фактические настройки и объясни их гарантии при dev replication factor 1.
- Отмечает событие опубликованным после подтверждения Kafka.
- Сохраняет event_id при повторе и восстанавливает незавершенную публикацию после остановки процесса.
- Два publisher не портят состояние друг друга; устаревший владелец не перезаписывает новое состояние.
- Не удаляет непереданные события из-за недоступности Kafka.

Окно «Kafka подтвердила запись, publisher упал до отметки published» приводит к возможному дубликату. Защита producer от повторов протокола Kafka не заменяет прикладную дедупликацию повторной публикации outbox. Опиши at-least-once, не обещай exactly-once всей распределенной системы.

При недоступности Kafka уже принятые переводы сохраняют событие в outbox; после восстановления publisher догоняет. Документируй лимиты backlog и поведение при исчерпании ресурсов. Нельзя сообщать успех записи, если SQL-транзакция не зафиксировалась.

Для уже существующих операций определи границу событий: по умолчанию новая схема публикует события новых операций после миграции. Не создавай повторные переводы ради заполнения Activity. Backfill старой истории — отдельная явно обозначенная задача, не обязательная для первой версии.

## 6. Kafka consumer, Inbox и проекция

Activity хранит inbox/event_id и модель чтения в собственной БД. В одной транзакции:
1. Регистрирует входное событие с уникальным event_id.
2. Добавляет записи активности и обновляет сводку.
3. Фиксирует обе части.

Offset подтверждается только после commit проекции. После сбоя между SQL commit и commit offset повтор события не меняет итог повторно. Ошибка обработки не должна незаметно продвигать offset.

Для первой версии используй последовательную обработку внутри каждой partition и параллельность между partitions. Если выбираешь более сложную конкурентность, докажи, что offset не перескакивает через незавершенное сообщение.

Модель чтения:
- Активность по счетам, направление, сумма, время и ссылка на операцию.
- Уникальность записи по event_id и account_id.
- Опциональная сводка входящих/исходящих операций; обновления должны быть идемпотентны и независимы от порядка.
- Для накопительных сумм используй типы без переполнения и потери точности.
- Это статистика и история, не авторитетный баланс кошелька.
- Пустая проекция не доказывает отсутствие счета; документируй семантику ответа.

Обработай malformed и неподдерживаемые события: понятная классификация ошибок, ограниченные повторы временных ошибок и DLQ для окончательно непригодных сообщений. Успешно доставь сообщение в DLQ до продвижения исходного offset. Если Kafka/DLQ недоступны, не считай сообщение обработанным. Дубликаты DLQ допускаются с устойчивым идентификатором исходного сообщения.

Проверь consumer groups, rebalance и повторный запуск. Входящая схема имеет версию; совместимые необязательные поля не должны ломать потребителя.

Replay в существующую проекцию не должен удваивать данные. Продемонстрируй повторную обработку сохраненного диапазона с новым group ID. Не удаляй inbox раньше горизонта допустимого replay. Для первой версии допустимо отсутствие автоматической очистки. Retention Kafka ограничивает доступную историю; не обещай восстановление событий, которых уже нет в брокере и которые отдельно не архивируются.

## 7. Redis: общий rate limiter

Реализуй общий лимит на аутентифицированного клиента и группу write-методов для нескольких Gateway. Идентификатор клиента должен быть одинаковым на разных экземплярах; не логируй и не используй сырой bearer token как публичный идентификатор.

Для первой версии достаточно окна от первого запроса с TTL:
- Один ключ на клиента и группу методов.
- Короткий Lua script атомарно выполняет INCR, установку TTL при первом запросе и чтение оставшегося TTL.
- Последующие запросы не продлевают окно.
- Не разбивай это на отдельные неатомарные клиентские команды.
- Лимит и длительность настраиваются; параметры валидируются.
- При превышении — HTTP 429 и корректный Retry-After.
- Для недоступности Redis выбери и документируй политику. По умолчанию write-запросы fail-closed с 503; недоступность Redis не выдается за превышение лимита.
- Идемпотентный повтор тоже является HTTP-запросом и учитывается в запросном лимите; это не меняет правила финансовой идемпотентности.

Проверь TTL, конкурентные запросы и общий бюджет двух Gateway. Объясни пограничные всплески fixed-window-подобного алгоритма и сброс состояния при потере Redis-данных. Не называй limiter абсолютной финансовой гарантией и не переноси в Redis остатки, журнал или дедупликацию денежных операций.

## 8. Наблюдаемость и локальное окружение

Добавь метрики:
- Возраст и размер outbox backlog, ошибки и повторы публикации.
- Consumer lag по partitions, дубликаты, DLQ и время появления операции в Activity.
- gRPC/HTTP latency и статусы, Redis errors и rate-limited requests.
- Пулы БД и bounded concurrency по фактически используемым компонентам.

В logs допустимы request_id, event_id и operation_id; не помещай их в Prometheus labels. Labels имеют ограниченную кардинальность.

Compose поднимает Gateway, LedgerCore, publisher, Activity, PostgreSQL, Kafka в KRaft-режиме и Redis. Для проверки rate limiter предусмотрены два Gateway. Prometheus можно вынести в дополнительный profile.

Для dev достаточно одного брокера с постоянным томом. Явно укажи replication factor 1 и отсутствие защиты от потери диска/узла; перезапуск одного брокера не является проверкой отказоустойчивости Kafka-кластера. Не добавляй трехброкерный кластер до готовности основных сценариев.

Зафиксируй образы и зависимости. Go-приложения собираются multi-stage и запускаются без root. Добавь health/readiness с короткими таймаутами и документированными зависимостями; недоступность асинхронной проекции не должна автоматически отменять уже зафиксированные переводы.

Постоянные данные не удаляются обычным make down. Очистка — отдельная явная команда только для локального тестового окружения.

## 9. Обязательные проверки

Сохрани исходные финансовые тесты и добавь реальные интеграционные проверки с PostgreSQL, Kafka, Redis и gRPC. Моки не заменяют проверки транзакций, consumer offsets и атомарности limiter.

Обязательные сценарии:
1. Перевод через Gateway/gRPC фиксирует одну операцию и одно логическое outbox-событие.
2. Отказ/rollback не создает событие; повтор ключа не создает новый перевод.
3. gRPC deadline или потеря ответа после commit разрешаются повтором с тем же ключом без двойного списания.
4. Kafka недоступна во время переводов: outbox накапливается, после восстановления Activity догоняет.
5. Остановка publisher после подтверждения Kafka до отметки published: повтор публикации не удваивает проекцию.
6. Остановка Activity после SQL commit до commit offset: повтор не меняет итог.
7. Rebalance с двумя consumers сохраняет полноту и отсутствие двойных эффектов.
8. Временная ошибка БД Activity не приводит к пропуску сообщения.
9. Дубликаты, поздняя отмена и перестановка событий дают корректную проекцию.
10. Невалидное/неподдерживаемое событие попадает в DLQ; сбой DLQ не вызывает молчаливой потери.
11. Replay не удваивает записи и счетчики.
12. Два Gateway совместно соблюдают один лимит; после TTL запросы снова проходят.
13. Redis outage дает документированный ответ; превышение лимита и отказ Redis различаются.
14. SIGTERM завершает компоненты ограниченно по времени, без потери уже зафиксированного outbox.
15. Исходная финансовая сверка и независимая сверка проекции проходят после аварийных сценариев.

Сверяй множества ID и суммы по журналу и проекции. Число Kafka deliveries может быть больше числа уникальных событий — это не ошибка само по себе. Невалидные события и DLQ учитываются отдельно от валидных операций.

Используй управляемые точки отказа только в тестовом режиме, изолированные БД и topics, ограниченный polling и общий deadline. Не синхронизируй сложные тесты одним произвольным time.Sleep.

В CI обязательны сборка, генерация/проверка актуальности proto, go vet, применимый линтер, unit и интеграционные проверки, go test -race для применимых пакетов. Нет доступа к Docker — честно NOT RUN, а не «все проверки пройдены».

## 10. Измерения и критерии приемки

Подготовь воспроизводимые локальные эксперименты:
- Gateway → gRPC → зафиксированный перевод: throughput, p50/p95/p99, ошибки и ответы limiter отдельно.
- Задержка от commit операции до видимости в Activity.
- Накопление и время догона backlog после фиксированного простоя Kafka/consumer.
- Результат replay: уникальные операции, события и строки проекции до/после.
- Совместный Redis-лимит двух Gateway под конкурентной нагрузкой.

Условия и сырые данные сохрани: версии, commit SHA, CPU/RAM, лимиты контейнеров, число клиентов/consumers, partitions, Kafka-настройки, пулы БД, размер набора и длительность. Делай несколько повторов и фиксируй ошибки. Не превращай короткий синтетический пакет в SLA.

Не переноси старые результаты LedgerCore, включая примерно 2248 переводов/с, на новый путь Gateway/gRPC/Redis без нового измерения. Не обещай, что добавление инфраструктуры ускорит перевод. Итоговое достижение может состоять в проверенных гарантиях и диагностике сбоев.

Документация:
- README: назначение каждой технологии и запуск одной командой.
- docs/architecture.md: синхронный путь и асинхронный путь событий, границы транзакций, источник истины.
- proto-контракты, схема Kafka-события, миграции, .env.example без секретов.
- 3–4 ADR: почему события после commit; outbox/inbox; ключ partition и порядок; политика Redis outage.
- docs/failure-scenarios.md, docs/benchmarks.md, docs/demo.md, краткий runbook.
- Makefile: make up, make down, make generate, make test, make test-integration, make lint, make build, make demo, make bench.

Демонстрация за 5–10 минут показывает перевод, появление Activity, остановку Kafka, накопление/догон outbox, безопасный повтор события и общий rate limiter двух Gateway. Финал — две сверки: исходного ledger и проекции. Повтор демонстрации не должен незаметно повторно финансировать те же счета.

## 11. Коммиты и отчет
