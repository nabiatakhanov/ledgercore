# Промпт: LedgerCore — учет переводов с неизменяемым журналом

Ты — самостоятельный Go backend-разработчик уровня middle. Реализуй законченный проект LedgerCore: сервис учета внутренних переводов с двойной записью, идемпотентностью, защитой от двойного списания и независимой сверкой остатков.

Проект предназначен для портфолио. Работай с файлами, терминалом и Git. Результат — запускаемый репозиторий, проверяемые гарантии, воспроизводимые эксперименты и последовательные коммиты. Это учебная учетная система с тестовыми средствами, без реального движения денег и подключения банков.

- Качество уровня middle: небольшие понятные пакеты, явные зависимости, осмысленные интерфейсы, корректная обработка ошибок, тесты существенных свойств. Не создавай универсальный framework и абстракции без потребителя.

## Денежная модель и инварианты

До кода зафиксируй определения в docs/invariants.md.

1. Суммы операций — положительное целое количество копеек в пределах int64. В HTTP используй строковое amount_minor, в Go — проверенный целочисленный тип, в БД — BIGINT. Float32/float64 для денежных значений запрещены.
2. Модель журнала: положительная signed delta увеличивает внутренний баланс счета, отрицательная уменьшает. В каждой проводимой операции сумма дельт равна нулю. Объясни связь этой нормализованной модели с дебетом и кредитом; не утверждай, что дебет всегда означает уменьшение для любых бухгалтерских счетов.
3. Успешный перевод создает ровно две записи: списание со счета отправителя и равное зачисление получателю. Счета различаются. Клиентские кошельки не могут иметь отрицательный остаток.
4. Существуют клиентские и защищенные системные счета. Для тестового начального финансирования используй отдельный балансирующий системный счет, которому разрешен отрицательный остаток. Нельзя создавать средства простым UPDATE баланса.
5. Публичный API создает клиентский кошелек с нулевым балансом и не позволяет списывать с системного счета. Начальные тестовые средства вносит только явно обозначенная административная fixture-команда через тот же механизм сбалансированного журнала.
6. Неизменяемый журнал — источник истины. Таблица текущих остатков является синхронно обновляемой проекцией и меняется в той же транзакции, что журнал.
7. Опубликованные записи журнала не изменяются и не удаляются прикладной ролью БД. Отмена — новая сбалансированная операция со ссылкой на исходную; максимум одна полная отмена на исходную операцию.
8. Отменять можно только обычный успешный перевод, не начальное финансирование и не другую отмену. Если у исходного получателя уже недостаточно средств для обратного списания, отмена отклоняется без частичных изменений.
9. Проверяй переполнение при расчете каждого нового остатка. Суммы при независимой сверке также должны вычисляться без переполнения; PostgreSQL NUMERIC и math/big допустимы для агрегатов.
10. Отказ, rollback и повтор запроса не оставляют половины перевода. Успех возвращается только после commit. Потеря ответа после commit разрешается повторным обращением с тем же ключом идемпотентности, а не предположением, что перевод не произошел.

## Схема и обеспечение целостности

Минимальные сущности: accounts, journal_transactions, postings, idempotency_records. Добавь связи, уникальности, ограничения и индексы под реальные запросы.

- Раздели роль миграций и прикладную роль. Прикладная роль не может UPDATE/DELETE записи опубликованного журнала; проверь это интеграционным тестом.
- Сбалансированность многорядной операции должна проверяться работающим механизмом БД на границе commit, например deferred constraint trigger. Обычный CHECK одной строки не может гарантировать сумму по нескольким записям.
- Проверяй как неправильные суммы, так и заголовок операции без записей; не оставляй обход через создание пустого journal_transaction. Для поддерживаемых видов операций проверяй ожидаемое количество и направление записей.
- Не называй систему защищенной от администратора БД. Опиши, какие инварианты обеспечивают ограничения БД, какие — алгоритм записи, какие нарушения обнаруживает сверка.
- Миграции должны применяться к чистой БД. Данные PostgreSQL сохраняются в отдельном томе Compose.

## Транзакции, конкуренция и идемпотентность

Выбери и обоснуй стратегию. Для этой версии подходит READ COMMITTED с блокировками всех затрагиваемых счетов в стабильном порядке по ID; альтернативу принимай только при наличии объяснения и тестов.

- Проверка доступного остатка, две записи журнала, изменение двух остатков и фиксация результата идемпотентности выполняются в одной транзакции.
- Не выполняй внешние HTTP-вызовы и долгую работу под блокировками.
- Одновременно приходящие переводы A→B и B→A не должны получать разный порядок блокировки счетов. У операций отмены должен быть совместимый порядок блокировок и проверка уникальности.
- Предусмотри bounded retry всей транзакции для применимых SQLSTATE, например serialization failure и deadlock. Не повторяй бизнес-отказы, не запускай бесконечные повторы и учитывай context deadline. Не теряй первоначальный ключ идемпотентности.
- Idempotency-Key обязателен для переводов и отмен. Область уникальности — вид операции + ключ в одном доверенном контуре. Уникальность обеспечивается БД, не только проверкой SELECT.
- Один ключ и одинаковые нормализованные параметры возвращают сохраненный результат; другие параметры дают 409. Fingerprint включает все поля, влияющие на результат. Числовые строки и идентификаторы нормализуются до сравнения.
- Успешный результат и окончательный бизнес-отказ, например insufficient_funds, сохраняются для повторов. Ошибки разбора до начала операции и инфраструктурные ошибки не превращай в навсегда закешированный бизнес-результат.
- При параллельном использовании ключа дождись окончания первой короткой транзакции в пределах deadline или верни документированный временный ответ. Не создавай второй перевод и не считай промежуточное состояние окончательным.
- Документируй неопределенность результата при разрыве соединения на commit и способ безопасного выяснения исхода.

## API и доступ

Опиши OpenAPI и реализуй:
- POST /v1/accounts — новый клиентский кошелек с нулевым балансом.
- GET /v1/accounts/{id} — баланс и метаданные.
- POST /v1/transfers — from_account_id, to_account_id, amount_minor, currency и ограниченные метаданные.
- GET /v1/transfers/{id} — результат и записи операции.
- POST /v1/transfers/{id}/reversal — полная отмена с новым Idempotency-Key.
- GET /v1/accounts/{id}/entries — история с ограниченным размером страницы и устойчивым cursor pagination.
- GET /livez, GET /readyz; отдельный служебный listener для метрик.

Это API доверенного внутреннего контура: статический bearer token из окружения, без заявления о готовой пользовательской авторизации и банковской безопасности. Добавь ограничения тела, строк и страниц, HTTP/DB timeouts, request_id и единый формат ошибок. Логи не содержат bearer token, ключей идемпотентности и чувствительных метаданных.

История и баланс должны иметь объясненную семантику чтения. Сверка использует один согласованный snapshot; нельзя сравнивать значения из разных моментов под параллельной нагрузкой.

## Независимая сверка и наблюдаемость

Команда ledgerctl reconcile:
- Пересчитывает остатки из журнала, сравнивает с проекцией accounts.
- Проверяет сбалансированность, отсутствующие записи, допустимость отмен и неотрицательность клиентских кошельков.
- Работает в согласованной read-only транзакции, возвращает ненулевой exit code при нарушении и выводит понятный отчет.
- Не исправляет данные автоматически. Демонстрация намеренного нарушения выполняется только на отдельной тестовой БД с административной ролью.

Метрики: операции по исходу, latency, повторы транзакций, конфликты идемпотентности, время ожидания блокировок или доступные показатели из выбранного инструментария, результаты сверки. Не помещай ID счетов, операций, ключи и тексты ошибок в labels. Добавь корректное завершение по SIGTERM, bounded shutdown и настройки пула БД.

## Обязательные тесты

Unit-тесты: Money, нормализация запросов, ошибки, overflow и модель переходов. Интеграционные тесты — с реальной PostgreSQL и прикладной ролью, без SQL-моков для проверки изоляции.

Проверь:
- Конкурентное списание с одного кошелька: принятые операции не превышают доступные средства, остаток не отрицателен.
- Встречные переводы и отмены сохраняют инварианты.
- Много запросов с одним ключом создают один результат и одну проводимую операцию.
- Другие параметры с тем же ключом дают 409.
- Повтор после потери ответа возвращает ранее зафиксированный результат.
- Остановка процесса до commit не оставляет часть операции.
- Недостаток средств не меняет журнал и остатки; повтор сохраненного отказа не становится успехом после последующего пополнения.
- Повторная отмена и отмена уже потраченных средств корректно отклоняются.
- Неправильная сумма записей и пустая операция не проходят commit.
- Прикладная роль не может переписать журнал.
- Переполнение и значения на границах обрабатываются контролируемо.
- Сверка не дает ложного расхождения под нагрузкой и обнаруживает намеренную порчу проекции.
- Пагинация соответствует документированному порядку и не дублирует записи уже существовавшего набора.

Добавь воспроизводимую последовательную модель случайных переводов с seed и сравнением состояния. В конкурентном сценарии проверяй журнал и инварианты, не предполагая заранее конкретный порядок commit.

Fault injection включается только тестовым режимом, а аварийные эксперименты запускаются на отдельной БД. Не используй произвольные sleep как единственный способ синхронизации. В CI запусти применимые go test -race, go vet, линтер, сборку и обязательные интеграционные проверки.

## Коммиты и календарь

Количество коммитов свободное: выбирай его по законченным изменениям. Код, относящиеся к нему тесты и необходимые изменения документации должны попадать в соответствующий этап. Дополнительные исправляющие коммиты разрешены. Не делай пустых коммитов ради количества и не применяй squash.

Параметры дат для этой версии промпта:
- COMMIT_DATE_MODE = historical
- COMMIT_DATE_START = 2025-05-8
- COMMIT_DATE_END = 2025-08-24
- COMMIT_TIMEZONE = Europe/Moscow, UTC+03:00

Диапазон можно изменить перед запуском. При режиме actual используй фактические даты и пропусти генерацию календаря. При historical соблюдай следующие правила:

1. Это заданные пользователем исторические метаданные Git, не измерение реальных трудозатрат. Первоначальное расписание сохрани в docs/commit-schedule.json с пометкой generated historical schedule и случайным seed.
2. Сначала составь список первоначальных коммитов N по границам работ. Первый датируй начальным днем, итоговый — конечным. Время выбирай случайно между 10:00:00 и 23:00:00 с минутами и секундами.
3. Интервал перед коммитом связывай со сложностью завершаемого изменения: небольшой config или документация — вес 1; обычная функция с тестами — 2; транзакции, анализ типов или конкурентность — 3; сложные аварийные проверки либо межпакетный анализ — 4.
4. Для N−1 интервалов умножь веса следующих коммитов на случайные коэффициенты 0.85–1.15 и нормализуй на доступный диапазон. После выбора календарных дат и времени проверь границы и строгое возрастание. При необходимости повтори генерацию. Не задавай жесткий минимум интервала: небольшое исправление может следовать в тот же день.
5. Выведи первоначальную таблицу дат и сообщений, затем продолжай без ожидания согласования. Не создавай коммиты до выполнения соответствующих работ.
6. При изменении плана перераспределяй только даты еще не созданных коммитов. Сохраняй уже записанную историю. На конечном дне оставляй запас времени для заключительных исправлений. Обновление расписания включай в очередной содержательный коммит.
7. Для каждого вызова git commit локально передавай одинаковые GIT_AUTHOR_DATE и GIT_COMMITTER_DATE в ISO 8601 с явным +03:00. Одного --date недостаточно для установки обеих дат. Имя и email используй из существующей Git identity; не выдумывай их.
8. После каждого коммита проверяй даты через git show --no-patch --pretty=fuller HEAD. В финале автоматически проверь новые коммиты в порядке родителей, а не сортировки по дате: все даты внутри диапазона, обе даты равны, каждый следующий коммит позднее предыдущего.
9. Не переписывай чужую историю и не меняй системные часы. При отсутствии Git identity сообщи о препятствии, сохрани работу и не объявляй отсутствующие коммиты созданными.

В финальном отчете покажи фактическое число новых коммитов, SHA, сообщения, AuthorDate и CommitDate.
